Docker容器无法访问宿主机映射端口排查：K8s遗留网络规则的坑

问题现象

宿主机上通过 Docker Compose 部署了一组服务，nginx 容器映射了 80 端口。从宿主机本地 curl 完全正常，但从同一台机器上的其他容器内访问宿主机 IP:80 却不通：

  • 宿主机 curl 192.168.16.81:80 ✅
  • 容器内 ping 192.168.16.81 ✅
  • 容器内 curl 192.168.16.81:80 ❌（即时失败）
  • 容器内访问宿主机其他端口（如 python http.server 的 8000）✅

关键发现：80 端口是 docker-proxy

80 端口不是原生宿主机服务，而是 docker-proxy 做的端口映射。正常情况下，同桥接网络的容器访问宿主机 IP 的映射端口，流量路径是：

Docker 的 DNAT 规则带有 ! -i br-xxx 排除条件，不会对同桥接来的流量做 DNAT，而是让 docker-proxy 以用户态代理方式转发。

抓包定位

SYN 包到达了宿主机（经过 veth → br-981d8afcd7df In），但没有任何回应——被静默 DROP。

根因：K8s 遗留的三层”幽灵防火墙”

这台宿主机之前跑过 K8s 集群，卸载后留下了三层互相叠加的网络规则：

第一层：Calico 的 iptables-legacy 规则

Calico 的 cali-INPUT 链对非 cali 接口的新建 TCP 连接执行 DROP。Docker 容器的流量从 br-981d8afcd7df 进来，不是 cali 接口，直接被丢弃。

第二层：br_netfilter 内核模块

K8s 要求加载 br_netfilter 并设置此参数为 1，让二层桥接流量也经过 iptables 处理。这意味着容器在桥接网络上发的包，本该只走 L2 转发，却被拉入 iptables 的 FORWARD/INPUT 链接受检查。

第三层：kube-proxy 的 nftables 规则

kube-proxy 在 PREROUTING 中注入了 KUBE-SERVICES 跳转，干扰了正常的 Docker NAT 流程。

为什么单独清除一层不够

操作 结果 原因
清空 Calico (iptables-legacy) 仍不通 br_netfilter 仍让桥接流量过 nftables FORWARD 链
关闭 bridge-nf-call-iptables 仍不通 KUBE-* 链还在 nftables NAT 表干扰 PREROUTING
只清 nftables 不重启 仍不通 Docker 自己的规则也被清了，需要重建

三层叠加，必须全部清除并让 Docker 重建自己的规则。

对比：正常环境为什么能通

另一台没装过 K8s 的机器，同样的 Docker 部署，容器内 curl 宿主机 IP:80 完全正常。因为：

  • 没有 br_netfilter，桥接流量不过 iptables
  • 没有 Calico/kube-proxy 残留规则
  • docker-proxy 用户态转发路径畅通

排查经验总结

  1. 先抓包：tcpdump 确认包到了哪里、有没有回应，比猜规则高效
  2. 注意双套 iptables：nftables 后端（iptables）和 legacy（iptables-legacy）是独立的，分别检查
  3. K8s 卸载不等于清理干净：iptables 规则、内核模块、sysctl 参数都不会自动清除
  4. br_netfilter 是隐藏杀手：让本不该被过滤的桥接流量进入 iptables，是很多容器网络”玄学问题”的根源
  5. docker-proxy vs DNAT：理解 Docker 端口映射的两条路径，能快速判断问题在哪一层
